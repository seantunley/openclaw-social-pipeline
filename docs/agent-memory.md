# Agent memory — what's built and why

This is the technical doc the original spec (msgs 25–27 of the agent-build
session) asked for: *"I want memory for my agent with the following criteria.
It must not forget anything. It must log and catalogue every conversation
with relevance. Preferences need to be remembered. It must follow the
memories and be able to recall them. … Build it all, all the upgrades, your
recommendations. And then I want the documentation, in details what you have
built and why."*

References that informed the design:

- *A Practical Guide to Memory for Autonomous LLM Agents* — Towards Data
  Science, 2024 (working / episodic / semantic / procedural framing).
- *Memory Scaling for AI Agents* — Databricks, 2024 (the "manage" step is
  where most systems fail).

The build follows the article's framing but skips the SaaS upsells and the
day-1 vector-DB churn. SQLite + drizzle, same database the rest of the
pipeline uses. No new infra.

---

## Tables

All in [engine/src/db/schema.ts](../engine/src/db/schema.ts), all created
in [engine/src/db/index.ts](../engine/src/db/index.ts).

### Episodic — `agent_message`
The raw record. Every user turn, every assistant turn, every tool call, every
tool result. **Never deleted, never summarised away.** Summaries are derived
and rebuildable; this table is the source of truth.

Schema highlights:
- `role` ∈ `user | assistant | tool | system`
- `content` text, plus `tool_calls` / `tool_name` / `tool_result` JSON
- `extracted_at` / `embedded_at` watermarks let the background worker skip rows
- FTS5 mirror: `agent_message_fts` (porter + unicode61 tokenizer)
- Vector mirror: `agent_message_vec` via [sqlite-vec](https://github.com/asg017/sqlite-vec)

### `agent_conversation`
Groups messages. One row per (surface, surface_ref) where `surface` is
`telegram | dashboard | system`. Soft-archived via `archived_at` — never
hard-deleted, so old conversations remain searchable.

### Semantic — `agent_fact`
LLM-extracted claims from messages.
- `type` ∈ `preference | fact | skill | relationship | goal | constraint`
- `subject` — who/what the fact is about (1–3 words)
- `content` — the claim itself, near-verbatim from the source message
- `source_message_id` — pointer back to the originating `agent_message`
- `confidence` 0–1, `reinforcement_count`, `last_seen_at`, `last_validated_at`
- `active` boolean (`false` = contradicted/deactivated, never deleted)
- `superseded_by_message_id` — provenance for deactivations
- FTS5 mirror: `agent_fact_fts`
- Vector mirror: `agent_fact_vec`

### Preferences — `user_preference`
Never-forget store, **loaded entirely every turn**. Distinct from `agent_fact`
because preferences are operationally always applicable, while facts are
situationally retrieved.
- `key` primary key, `value` text
- `set_explicitly` — `true` when user stated it, `false` when agent inferred
- `set_via_message_id` — provenance pointer

### Procedural — `conversation_summary`
Per-conversation rollups, generated by the cron worker after a conversation
goes idle.
- `period` ∈ `turn | day | week | conversation`
- `start_message_id` / `end_message_id` define the span
- `summarizer_model` records which cheap model produced it

### Procedural / reflective — `agent_lesson`
Behavioural rules the agent self-extracts after a conversation ends. Distinct
from facts: lessons are imperatives ("next time the operator asks X, do Y
first"), facts are statements about the world.

## Read path (every chat turn)

In [engine/src/services/agent/retriever.ts::recall](../engine/src/services/agent/retriever.ts) → composed by [runtime.ts::chat](../engine/src/services/agent/runtime.ts):

1. **Last 12 messages of this conversation** → working memory. Injected as a
   "Conversation so far (this thread)" block.
2. **All active `user_preference` rows** → injected verbatim. Every turn,
   no exceptions.
3. **Latest `conversation_summary`** for this thread → injected when present.
4. **FTS5 + sqlite-vec hybrid retrieval** over `agent_message` and
   `agent_fact`. Both lexical and semantic hits are fused via reciprocal
   rank fusion (RRF). Top 8 message hits + top 12 fact hits.
5. **Active `agent_lesson` rows** with confidence ≥ 0.5.

The composed system prompt order is:
```
You are {agent.name}.
{agent.system_prompt}

{operator preferences block}
{lessons block}
{conversation summary block}
{recalled fact block}
{recalled message snippets block}
{working memory block — recent turns}

{tools registry as JSON}
```

**Confidence floor for fact injection is 0.7** per the original brief's
manage-step rule. Weak inferences stay in the table but don't bias the prompt.

## Write path

After every chat turn the runtime calls `scheduleBackground()` which fires
the extractor + embedder for both the user's message and the assistant's
reply, non-blocking. None of this delays the user-visible reply.

In addition, the cron-style **memory worker** runs every 60 seconds:

| Pass        | What it does                                                                  | Source file                                                  |
|-------------|-------------------------------------------------------------------------------|--------------------------------------------------------------|
| Extract     | LLM extracts facts / preferences from `agent_message.extracted_at IS NULL` rows | [extractor.ts](../engine/src/services/agent/extractor.ts)    |
| Embed       | OpenAI `text-embedding-3-small` for `embedded_at IS NULL` messages + facts    | [embed-writer.ts](../engine/src/services/agent/embed-writer.ts) |
| Summarise   | One paragraph per conversation, run after 30 min idle                         | [summarizer.ts](../engine/src/services/agent/summarizer.ts)  |
| Reflect     | Behavioural lessons after 30 min idle (same trigger as summary)               | [reflector.ts](../engine/src/services/agent/reflector.ts)    |

Worker is in [memory-worker.ts](../engine/src/services/agent/memory-worker.ts),
started alongside the scheduler from [server.ts](../engine/dashboard-api/server.ts).

### Extractor

Cheap model (Haiku-class). Strict no-fabrication system prompt — extracts
only claims VERBATIM from the source message. Confidence < 0.4 are discarded.

For preferences (extracted only from user-role messages), the extractor
calls `preferences.upsert()` which both records the value AND creates an
`agent_fact` row for cross-recall.

For facts, the extractor calls `facts.upsertFact()` which:
- Dedupes by substring overlap on (subject, type) → bumps
  `reinforcement_count` instead of inserting a duplicate.
- Adds 0.05 confidence on reinforcement (capped at 1.0).

### Embedder

Uses OpenAI `text-embedding-3-small` (1536 dim). Vectors stored in the
`*_vec` virtual tables. When `OPENAI_API_KEY` is unset, the embedder falls
back to deterministic SHA-256-seeded stub vectors and logs a warning — the
embedded_at flag still gets set so the worker doesn't re-try every tick, but
vector recall is FTS-only until a real key is configured.

### Summariser

After ≥ 6 turns and ≥ 30 min idle, runs `summarizeConversation` which
overwrites the existing `conversation_summary` row for `period='conversation'`.
Each summary is a tight paragraph (4–8 sentences) preserving every concrete
value mentioned (names, dates, numbers, URLs).

### Reflector

Same trigger. Reads the full conversation and looks for grounded behavioural
lessons: corrections the operator gave, approaches they confirmed,
recurring preferences. Extracted lessons get inserted into `agent_lesson`,
or reinforce existing matching lessons by `reinforcement_count + 1`.

## Manage step — preventing memory rot

Per the article's lesson: "Most systems fail at the manage step."

1. **Deduplication** — `agent_fact.upsertFact` substring-matches new content
   against existing active rows on the same (subject, type). Match →
   reinforcement; no match → insert.
2. **Contradiction detection** — for preferences this is automatic
   (`upsert(key, newValue)` replaces). For facts, the runtime exposes
   `facts.supersede(id, supersededByMessageId)` for the extractor to call
   when a new turn explicitly contradicts. (Currently invoked manually via
   the upcoming Memory inspection UI; an LLM-driven contradiction extractor
   is the next iteration.)
3. **No age decay** — facts and lessons are never expired by age. Only
   contradictions deactivate.
4. **Confidence floor 0.7 for injection** — weak inferences live in the
   table but don't bias the prompt.

## What was built versus what was deferred

### Built (Layer 1 — the spec)
- Five tables + 2 FTS5 mirrors
- Read composer (`recall`)
- Write extractor (`extractor.ts`)
- Cron rollup (`memory-worker.ts`)

### Built (the "all upgrades" the operator authorised in msg 27)
- `sqlite-vec` virtual tables for semantic recall, blended with FTS via RRF
- `agent_lesson` + reflector — the reflective procedural memory the article
  describes as the next layer up

### NOT built (per the brief's "what NOT to build now")
- External memory SaaS (Zep, Mem0). Your data, your control.
- Token-window compression. We keep raw episodic; we retrieve selectively.
- Memory-engine framework abstraction. The whole stack is ~10 plain TS
  modules of database CRUD. Three table writes, four reads. Not a framework.

### Backlog (operationally useful, not yet built)
- LLM-driven contradiction extractor that calls `facts.supersede()` on
  semantically opposite new claims (vs the current substring-overlap merge).
- Operator-facing Memory inspection UI (view / edit / deactivate prefs,
  facts, lessons). API endpoints already exist at
  `/api/social/agent/memory` and `/api/social/agent/preferences`.
- Per-day / per-week summary buckets (`period='day' | 'week'`). The
  `conversation_summary` table supports them; the summariser currently
  only writes `period='conversation'`.

## Configuration

Env vars (engine/.env):

| Var                                  | Default | What it controls                                              |
|--------------------------------------|---------|---------------------------------------------------------------|
| `AGENT_EMBED_DIM`                    | 1536    | Vector dimension. Must match the embedding model.             |
| `AGENT_EMBED_MODEL`                  | text-embedding-3-small | OpenAI embedding model id.                     |
| `OPENAI_API_KEY`                     | —       | When unset, vectors are deterministic stubs (warned in logs). |
| `MEMORY_WORKER_POLL_MS`              | 60_000  | Memory worker tick interval.                                  |
| `MEMORY_WORKER_BATCH_EXTRACT`        | 20      | Max messages to extract per tick.                             |
| `MEMORY_WORKER_BATCH_EMBED`          | 50      | Max items to embed per tick.                                  |
| `MEMORY_WORKER_SUMMARY_IDLE_MIN`     | 30      | Minutes a conversation must be idle before summary/reflect.   |
| `MEMORY_WORKER_REFLECT_MIN_TURNS`    | 6       | Minimum turns before reflect runs on a conversation.          |

## How to verify it works end-to-end

1. `cd engine && npm run start:api`
2. Hit `POST /api/social/agent/preferences` with `{key: "tone", value: "..."}`.
3. Open the dashboard, click the chat button, ask the agent something that
   should be tone-sensitive ("draft a quick reply about X"). It should use
   that tone.
4. In the same conversation, tell it a one-off fact ("my favourite colour is
   teal — remember that"). On the next turn ask "what colour did I say?" —
   it should answer correctly because (a) working memory injects last N
   turns, (b) the extractor will write a `preference` fact for it in the
   background.
5. Watch the API logs after 60 seconds — the memory worker tick should log
   when there's something to do.

## Upgrade path (when you're ready)

| Trigger                               | Upgrade                                                      | Effort     |
|---------------------------------------|--------------------------------------------------------------|------------|
| 10k+ messages, FTS misses recall      | Already there — sqlite-vec is wired                          | ✅ done    |
| Slow on > 100k messages               | Add HNSW index on `agent_message_vec`                        | ½ day      |
| You outgrow SQLite                    | Postgres + pgvector. Drizzle is dialect-portable.            | day–week   |
| Multi-agent shared memory             | Promote `agent_fact` + `user_preference` to a service       | ~1 day     |
| LLM-driven contradiction detection    | Second extractor pass that compares new claims to active ones | ½ day      |
